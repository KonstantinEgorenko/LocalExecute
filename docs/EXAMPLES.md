# Example tasks and acceptance

These scenarios illustrate how to scope work and interpret its output. They are examples, not records of successful live runs. The only invocation walkthrough is in [installation](INSTALLATION.md).

| Scenario | Initial objective and scope | Expected workflow and evidence | When it should stop |
| --- | --- | --- | --- |
| Small single-file bugfix | Fix a minimum-clamp function. Keep its signature and add below/equal/above regression cases in the separate demo target | Lead plans. Router selects an eligible worker. The worker edits source and tests in a candidate. Configured checks, Critic and Judge review the exact revision. Inspect the diff, verification report and final result | Missing model, infeasible plan, invalid edit, failed checks or missing Judge acceptance |
| Multi-file change | Make two modules agree on cache key normalization while preserving their public API. Limit changes to the relevant implementation and tests | Planner identifies the cross-module dependency. Worker inspects both modules and changes the relevant files. Require existing tests and a boundary integration case. Inspect candidate provenance and per-Todo results | Scope conflict, regressions, missing cross-module evidence or plan too broad for the available profiles |
| Verification failure and recovery | Correct a parser while retaining rejection of malformed input. Assume the first candidate breaks a baseline case | Deterministic verification records the failure. Bounded recovery can pass the failure evidence to a later execution slice or allow a typed replan. Require fresh checks on the revised candidate. Inspect the recovery record and final verdict | Recovery budget exhausted, stale or unauthorized draft, unresolved failing baseline |
| Research-assisted change | Update a compatibility adapter after checking an official upstream API reference. Keep external evidence and implementation evidence distinct | An explicitly configured research path can gather and retain references. Planning and execution use only allowed context. Verify with local compatibility tests and inspect citations, candidate evidence and acceptance | Missing provider, unsupported research configuration, unverifiable source or failed verification |

The public offline suite exercises native SIMPLE and REPLAN lifecycle behaviors using deterministic model transport. Provider-backed research and the example outcomes above require separate qualification. Use the [validation matrix](VALIDATION.md) to distinguish tested paths from illustrative scenarios.
